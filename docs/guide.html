KioMQ

The building blocks for running background work inside a Tokio service: a queue to enqueue jobs, workers to process them, and a pluggable store to keep the state everyone agrees on.

Section 01

Overview

KioMQ provides the core building blocks to run background work inside your Tokio services, inspired by BullMQ's ergonomics and implemented as an embeddable Rust library.

  • A Queue to enqueue tasks and jobs.
  • One or more workers to process jobs concurrently.
  • Pluggable stores: InMemoryStore (ephemeral), RedisStore (durable, distributed), and RocksDbStore (under construction).
  • Scheduling: delays, cron expressions, repeat policies.
  • Reliability: retries, backoff strategies, stalled-job detection.
  • Observability: events, progress updates, per-worker and per-process metrics.

Key features

  • Async and sync processors: async for I/O-bound work, sync via spawn_blocking for CPU-bound work.
  • Configurable concurrency, defaulting to the CPU count.
  • Event-driven idle workers, using lock-free atomics and Notify for near-zero CPU when empty.
  • Bulk enqueue via Queue::bulk_add and Queue::bulk_add_only.
  • Priority and delayed jobs, by score or after N milliseconds or a cron schedule.
  • Repeat policies: cron, backoff-driven, fixed interval, immediate.

Section 04

Workers

A worker takes a processor closure and drives it against the queue. Nothing runs until run() is called; close() shuts it down.

Async worker

use std::sync::Arc;
use kiomq::{InMemoryStore, Job, KioError, Queue, Worker, WorkerOpts};

#[tokio::main]
async fn main() -> kiomq::KioResult<()> {
    let store: InMemoryStore<u64, u64, ()> = InMemoryStore::new(None, "demo");
    let queue = Queue::new(store, None).await?;

    let processor = |_store: Arc<_>, job: Job<u64, u64, ()>| async move {
        Ok::<u64, KioError>(job.data.unwrap_or_default() * 2)
    };

    let worker = Worker::new_async(&queue, processor, Some(WorkerOpts::default()))?;
    worker.run()?;

    queue.bulk_add_only((0..10u64).map(|i| (format!("job-{i}"), None, i))).await?;

    let updating_metrics = queue.current_metrics.clone();
    // wait for all jobs to complete
    while !updating_metrics.all_jobs_completed() {
        tokio::task::yield_now().await;
    }
    worker.close();
    Ok(())
}

Sync worker

Sync processors run on a blocking thread via tokio::task::spawn_blocking, which suits heavy computation, hashing, blocking FFI and similar work.

use std::sync::Arc;
use kiomq::{InMemoryStore, Job, KioError, Queue, Worker, WorkerOpts};

#[tokio::main]
async fn main() -> kiomq::KioResult<()> {
    let store: InMemoryStore<u64, u64, ()> = InMemoryStore::new(None, "demo-sync");
    let queue = Queue::new(store, None).await?;

    let processor = |_store: Arc<_>, job: Job<u64, u64, ()>| {
        Ok::<u64, KioError>(job.data.unwrap_or_default() * 2)
    };

    let worker = Worker::new_sync(&queue, processor, Some(WorkerOpts::default()))?;
    worker.run()?;

    queue.add_job("compute", 42u64, None).await?;

    let updating_metrics = queue.current_metrics.clone();
    while !updating_metrics.all_jobs_completed() {
        tokio::task::yield_now().await;
    }
    worker.close();
    Ok(())
}
Section 05

Panics & errors in the processor

A processor signals a job failure by returning Err. The worker catches the error, marks the job failed, and retries it with the configured backoff depending on the attempts configuration.

!

Panics are caught tooA panic inside a processor is treated as a failure, so a rogue job cannot bring down the whole process.

Async backtrace with #[framed]

Annotate a processor with framed, re-exported from async-backtrace as kiomq::framed, for richer async stack traces:

use std::sync::Arc;
use kiomq::{framed, InMemoryStore, Job, KioError, Queue, Store, Worker, WorkerOpts};

#[framed]
async fn my_processor<S: Store<u64, u64, ()>>(
    _store: Arc<S>,
    job: Job<u64, u64, ()>,
) -> Result<u64, KioError> {
    let data = job.data.unwrap_or_default();
    if data == 0 {
        // Returning Err marks the job as failed and triggers a retry
        // (up to `attempts` times, as set in QueueOpts / JobOptions).
        return Err(std::io::Error::new(std::io::ErrorKind::Other, "zero input").into());
    }
    Ok(data * 2)
}
Section 06

Configuration

Queue options

use kiomq::{BackOffJobOptions, BackOffOptions, KeepJobs, QueueEventMode, QueueOpts,
            RemoveOnCompletionOrFailure};

let queue_opts = QueueOpts {
    attempts: 2,
    default_backoff: Some(BackOffJobOptions::Opts(BackOffOptions {
        type_: Some("exponential".into()),
        delay: Some(200),
    })),
    remove_on_fail: Some(RemoveOnCompletionOrFailure::Opts(KeepJobs {
        age: Some(3600), // keep for 1 hour
        count: None,
    })),
    event_mode: Some(QueueEventMode::PubSub),
    ..Default::default()
};
OptionPurpose
attemptsDefault number of attempts before a job is marked failed.
default_backoffBackoff strategy between attempts, for example exponential with a base delay in milliseconds.
remove_on_failRetention for failed jobs, by age in seconds or by count.
remove_on_completeThe same retention controls for completed jobs.
event_modeHow events are delivered, for example QueueEventMode::PubSub.

Per-job options

use kiomq::JobOptions;

let opts = JobOptions { attempts: 5, ..Default::default() };

Worker options

use kiomq::WorkerOpts;

let opts = WorkerOpts { concurrency: 8, ..Default::default() };

Concurrency defaults to the CPU count when left at the default.

Section 07

Events & observability

Subscribe to job-state events on the queue. Listeners are identified by an id so they can be removed again.

use kiomq::{EventParameters, InMemoryStore, JobState, Queue};

// Subscribe to a specific state.
let listener_id = queue.on(JobState::Completed, |evt| async move { let _ = evt; });

// Subscribe to all events.
let listener_id2 = queue.on_all_events(|evt: EventParameters<u64, ()>| async move { let _ = evt; });

// Remove a listener when no longer needed.
queue.remove_event_listener(listener_id);
Section 08

Progress updates

Report progress from inside a processor with Job::update_progress. It persists to the store and emits a progress event.

use std::sync::Arc;
use kiomq::{Job, KioError, Store};

async fn processor<S: Store<u64, u64, u8>>(
    store: Arc<S>,
    mut job: Job<u64, u64, u8>,
) -> Result<u64, KioError> {
    // update_progress persists to the store and emits a progress event.
    job.update_progress(50u8, store.as_ref()).await?; // 50% done
    // use job.update_progress_sync when using the Sync Worker
    Ok(job.data.unwrap_or_default() * 2)
}
Section 09

Process & worker metrics

KioMQ collects two kinds of metrics in the background with no extra setup. Both are stored with a TTL and refreshed by the queue's timer subsystem.

Process metrics

A process-level snapshot refreshed at a regular interval (PROCESS_METRIC_UPDATE_INTERVAL) and stored with a TTL. Each snapshot captures:

  • process_cpu_usage: CPU usage of the process tree, as a percentage.
  • memory_usage: RSS memory in bytes.
  • memory_stats: heap allocator statistics via the built-in Heapster instrumented allocator.
  • rt_metrics: Tokio runtime counters covering thread count, live tasks, park counts and busy durations.
  • workers: a Vec<WorkerMeta> with the state, options and active-job count of every registered worker.
  • hostname and pid: process identity.
// keyed by PID so multi-process deployments can be distinguished
let snapshots: std::collections::BTreeMap<u32, ProcessMetrics> =
    queue.fetch_proess_metrics().await?;

if let Some(m) = snapshots.values().next() {
    println!(
        "cpu: {:.1}%  mem: {} MB  tokio workers: {}",
        m.process_cpu_usage,
        m.memory_usage / 1_024 / 1_024,
        m.rt_metrics.workers_count,
    );
}

Worker metrics

Fine-grained, per-worker timing data for every in-flight job, useful for latency profiling and capacity planning:

let worker_metrics = queue.fetch_worker_metrics().await?;

for (worker_id, wm) in &worker_metrics {
    for task in &wm.tasks {
        println!(
            "worker {worker_id}  polls={}  idle={:?}",
            task.metrics.total_poll_count,
            task.metrics.total_idle_duration,
        );
    }
}
Section 10

Backends

In-memory

InMemoryStore is ideal for tests, development and short-lived tasks. It has no external dependencies.

Redis (default feature)

For durable, distributed workloads. Requires a running Redis instance:

docker run --rm -p 6379:6379 redis:latest
use kiomq::{Config, KioResult, Queue, RedisStore, SharedRedis};

#[tokio::main]
async fn main() -> KioResult<()> {
    // `Config` can be imported from `kiomq` or from `deadpool_redis`
    // (if you already use it in your app).
    let config = Config::default();
    let redis_conn = SharedRedis::create(&config)?;
    let store = RedisStore::new(None, "my-queue", &redis_conn).await?;
    let queue: Queue<(), (), (), _> = Queue::new(store, None).await?;
    // ... worker logic below here
    Ok(())
}

RocksDB Under construction

Embedded persistence, currently a work in progress.

[dependencies]
kiomq = { version = "0.1", default-features = false, features = ["rocksdb-store"] }
use kiomq::{temporary_rocks_db, RocksDbStore, KioResult, Queue};
use std::sync::Arc;

#[tokio::main]
async fn main() -> KioResult<()> {
    // replace `temporary_rocks_db` with a real database instantiation
    // (check out the rocksdb crate)
    let db = Arc::new(temporary_rocks_db());

    let store = RocksDbStore::new(None, "test", db.clone())?;
    let queue = Queue::new(store, None).await?;
    // ... worker logic below here
    Ok(())
}
Section 11

Benchmarks & testing

cargo bench

Run the test suite with cargo nextest:

cargo nextest run
!

Use nextest, not cargo testThe integration tests share process-global state (the metrics collector), so each needs its own process, which nextest does by default. Under cargo test, which uses a single process, they interfere with one another and fail. CI runs nextest and local development should too. The .config/nextest.toml profile also terminates any hung test so a stall fails fast instead of wedging the run.
