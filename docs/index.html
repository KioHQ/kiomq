Background jobs that stay in your service.

KioMQ is an embeddable task queue and orchestration library for Tokio. Enqueue work, process it concurrently, retry it when it fails, without standing up a separate job runner.

use std::sync::Arc;
use kiomq::{InMemoryStore, Job, KioError, Queue, Worker, WorkerOpts};

#[tokio::main]
async fn main() -> kiomq::KioResult<()> {
    let store: InMemoryStore<u64, u64, ()> = InMemoryStore::new(None, "demo");
    let queue = Queue::new(store, None).await?;

    let processor = |_store: Arc<_>, job: Job<u64, u64, ()>| async move {
        Ok::<u64, KioError>(job.data.unwrap_or_default() * 2)
    };

    let worker = Worker::new_async(&queue, processor, Some(WorkerOpts::default()))?;
    worker.run()?;

    queue.bulk_add_only((0..10u64).map(|i| (format!("job-{i}"), None, i))).await?;

    let updating_metrics = queue.current_metrics.clone();
    while !updating_metrics.all_jobs_completed() {
        tokio::task::yield_now().await;
    }
    worker.close();
    Ok(())
}
// Sync processors run on a blocking thread via tokio::task::spawn_blocking:
// suitable for heavy computation, hashing or blocking FFI.
let processor = |_store: Arc<_>, job: Job<u64, u64, ()>| {
    Ok::<u64, KioError>(job.data.unwrap_or_default() * 2)
};

let worker = Worker::new_sync(&queue, processor, Some(WorkerOpts::default()))?;
worker.run()?;

queue.add_job("compute", 42u64, None).await?;

Why KioMQ

A queue, workers and a store.
Nothing else to deploy.

Inspired by BullMQ's ergonomics, implemented as an embeddable Rust library. Start in-memory in a test, move to Redis in production without rewriting your processors.

Scale up

Many workers per process, concurrency defaulting to the CPU count. Async processors for I/O-bound work, sync ones on a blocking pool for CPU-bound work.

Scale out

Point several processes at one Redis instance and the same queue spreads across machines. Job state, metrics and events all live in the store.

Idle means idle

Workers park on a Tokio Notify and lock-free atomics rather than polling, so an empty queue costs near-zero CPU.

Retries and backoff

Per-queue and per-job attempt counts, exponential or fixed backoff, and stalled-job detection for work whose worker disappeared.

Scheduling

Delay a job by milliseconds, give it a priority score, or hand it a cron expression and a repeat policy and let the timer subsystem drive it.

Observability built in

Job-state events, progress updates, per-worker task timings and process-level CPU, memory and Tokio runtime metrics, all collected automatically.

How it works

Three moving parts.

A queue writes jobs to a store, workers claim them, and the store keeps the state everyone agrees on.

01

Create a queue

Pick a store (InMemoryStore for tests and short-lived work, RedisStore when the work has to survive a restart) and wrap it in a Queue.

02

Attach a worker

Give Worker::new_async or new_sync a closure. It receives the store and the job, and returns Ok or Err. Call run() to start it.

03

Add jobs

add_job for one, bulk_add for many. Workers wake on the notification, process concurrently, and update the store as they go.

Scheduling

Later, repeatedly, or in a strict order.

Jobs do not have to run now. Delay them, prioritise them, or attach a repeat policy and let KioMQ's timer subsystem re-enqueue them on schedule.

  • Delay by N milliseconds
  • Cron expressions for recurring work
  • Fixed-interval, immediate and backoff-driven repeats
  • Priority ordering by score
use kiomq::JobOptions;

// Five attempts before the job is marked failed.
let opts = JobOptions { attempts: 5, ..Default::default() };

queue.add_job("send-invoice", invoice_id, Some(opts)).await?;
Reliability

A rogue job cannot take the process down.

A processor signals failure by returning Err. Panics are caught too, and treated as failures, so the worker marks the job failed and retries it with the configured backoff.

  • Panics caught and converted to failures
  • Exponential or fixed backoff between attempts
  • Stalled-job detection
  • Richer async traces with #[framed]
let queue_opts = QueueOpts {
    attempts: 2,
    default_backoff: Some(BackOffJobOptions::Opts(BackOffOptions {
        type_: Some("exponential".into()),
        delay: Some(200),
    })),
    remove_on_fail: Some(RemoveOnCompletionOrFailure::Opts(KeepJobs {
        age: Some(3600), // keep for 1 hour
        count: None,
    })),
    ..Default::default()
};
Observability

You already know what the queue is doing.

Subscribe to job-state events, report progress from inside a processor, and read back per-worker timings and process metrics. No extra setup: they are collected in the background and stored with a TTL.

  • Per-state or catch-all event listeners
  • Progress persisted to the store
  • CPU, RSS, heap and Tokio runtime counters
  • Snapshots keyed by PID for multi-process deployments
// Subscribe to a specific state.
let listener_id = queue.on(JobState::Completed, |evt| async move {
    println!("completed: {evt:?}");
});

// Or to everything.
let all = queue.on_all_events(|evt: EventParameters<u64, ()>| async move {
    println!("{evt:?}");
});

queue.remove_event_listener(listener_id);
