Getting started

From empty project to first job.

Ten minutes, one dependency, no broker to install. By the end you will have a worker draining a queue, retrying failures and reporting progress.

Step one

Prerequisites

A recent stable Rust toolchain and a Tokio multi-thread runtime. That is the whole list for the in-memory backend.

KioMQ spawns workers as Tokio tasks, so the current-thread runtime will technically run but will not give you real concurrency. Use the multi-thread flavour:

[dependencies]
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
i

Redis is optionalEverything below works with the in-memory store. Redis only becomes necessary when jobs must outlive the process.

Step two

Install

cargo add kiomq

Or by hand:

[dependencies]
kiomq = "0.2.1"

Cargo features: redis-store (default), rocksdb-store, and tracing. To drop the Redis dependency entirely:

[dependencies]
kiomq = { version = "0.2.1", default-features = false }
Step three

Your first job

A queue, a processor closure, a worker. Copy this into src/main.rs and run it.

use std::sync::Arc;
use kiomq::{InMemoryStore, Job, KioError, Queue, Worker, WorkerOpts};

#[tokio::main]
async fn main() -> kiomq::KioResult<()> {
    let store: InMemoryStore<u64, u64, ()> = InMemoryStore::new(None, "demo");
    let queue = Queue::new(store, None).await?;

    let processor = |_store: Arc<_>, job: Job<u64, u64, ()>| async move {
        Ok::<u64, KioError>(job.data.unwrap_or_default() * 2)
    };

    let worker = Worker::new_async(&queue, processor, Some(WorkerOpts::default()))?;
    worker.run()?;

    queue.bulk_add_only((0..10u64).map(|i| (format!("job-{i}"), None, i))).await?;

    let updating_metrics = queue.current_metrics.clone();
    // wait for all jobs to complete
    while !updating_metrics.all_jobs_completed() {
        tokio::task::yield_now().await;
    }
    worker.close();
    Ok(())
}
cargo run

Ten jobs are enqueued, the worker doubles each number, and the process exits once the metrics report everything complete.

Step four

What just happened

Four pieces are doing the work, and they are worth naming because the rest of the library builds on them.

The store

InMemoryStore<D, R, P> holds job state. The three type parameters are the job data, the processor's return type, and the progress type. Here they are u64, u64 and () because this job carries a number, returns a number, and reports no progress.

The queue

Queue::new(store, opts) owns the store, exposes add_job and bulk_add, and runs the timer subsystem that drives delays, repeats and metric collection. Passing None for options accepts the defaults.

The processor

A closure taking Arc<Store> and a Job, returning Result. The store handle is there so a processor can enqueue follow-up work or read state without a captured reference.

The worker

Worker::new_async for I/O-bound work; Worker::new_sync when the job is CPU-bound, which runs it on a blocking thread via spawn_blocking. Nothing is processed until you call run(), and close() shuts the worker down cleanly.

i

Concurrency defaults to your CPU countOverride it with WorkerOpts { concurrency: 8, ..Default::default() }.

Step five

Handling failures

Return Err and the worker marks the job failed, then retries it according to the attempt count and backoff policy.

use kiomq::{QueueOpts, BackOffJobOptions, BackOffOptions};

let queue_opts = QueueOpts {
    attempts: 3,
    default_backoff: Some(BackOffJobOptions::Opts(BackOffOptions {
        type_: Some("exponential".into()),
        delay: Some(200),
    })),
    ..Default::default()
};

let queue = Queue::new(store, Some(queue_opts)).await?;

Per-job options override the queue default:

use kiomq::JobOptions;

let opts = JobOptions { attempts: 5, ..Default::default() };
queue.add_job("flaky-http-call", payload, Some(opts)).await?;
!

Panics are caughtA panic inside a processor is treated as a failure rather than being allowed to unwind into the runtime, so one bad job cannot take the process down with it.

For richer async stack traces, annotate the processor with #[framed], re-exported from async-backtrace:

use kiomq::{framed, Job, KioError, Store};
use std::sync::Arc;

#[framed]
async fn my_processor<S: Store<u64, u64, ()>>(
    _store: Arc<S>,
    job: Job<u64, u64, ()>,
) -> Result<u64, KioError> {
    let data = job.data.unwrap_or_default();
    if data == 0 {
        return Err(std::io::Error::new(std::io::ErrorKind::Other, "zero input").into());
    }
    Ok(data * 2)
}
Step six

Reporting progress

Long-running jobs can report where they are. Progress is persisted to the store and emitted as an event.

The progress type is the third parameter on the store. Change it from () to something meaningful, here a u8 percentage:

use std::sync::Arc;
use kiomq::{Job, KioError, Store};

async fn processor<S: Store<u64, u64, u8>>(
    store: Arc<S>,
    mut job: Job<u64, u64, u8>,
) -> Result<u64, KioError> {
    job.update_progress(50u8, store.as_ref()).await?; // 50% done
    Ok(job.data.unwrap_or_default() * 2)
}

In a sync worker, use update_progress_sync instead. Listen for the updates from anywhere with a queue handle:

let id = queue.on(JobState::Progress, |evt| async move {
    println!("progress: {evt:?}");
});
Step seven

Moving to Redis

Swap the store, keep the processor. Jobs now survive restarts and spread across every process pointed at the same Redis.

docker run --rm -p 6379:6379 redis:latest
use kiomq::{Config, KioResult, Queue, RedisStore, SharedRedis};

#[tokio::main]
async fn main() -> KioResult<()> {
    // `Config` can be imported from `kiomq` or from `deadpool_redis`
    // (if you already use it in your app).
    let config = Config::default();
    let redis_conn = SharedRedis::create(&config)?;
    let store = RedisStore::new(None, "my-queue", &redis_conn).await?;
    let queue: Queue<(), (), (), _> = Queue::new(store, None).await?;
    // ... worker logic below here
    Ok(())
}

The second argument to RedisStore::new is the queue name, and it is also the namespace for keys in Redis. Two processes using the same name share one queue; two processes using different names do not see each other's work.

Step eight

Testing your jobs

Use InMemoryStore in tests and ask for the multi-thread runtime, otherwise the worker has nowhere to make progress:

#[tokio::test(flavor = "multi_thread")]
async fn processes_a_job() {
    let store: InMemoryStore<u64, u64, ()> = InMemoryStore::new(None, "test");
    let queue = Queue::new(store, None).await.unwrap();
    // ... enqueue, run a worker, assert on the result
}
!

Run the suite with nextestKioMQ's own integration tests share process-global state (the metrics collector), so they need a process each. Use cargo nextest run rather than cargo test.
