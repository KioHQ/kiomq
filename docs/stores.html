Extending KioMQ

Custom stores.

A queue is only as portable as its storage. Store is a public trait, so you can back KioMQ with whatever your infrastructure already runs, and prove it correct with the same conformance suites the built-in stores are held to.

Motivation

When to write one

Three stores ship with KioMQ. A fourth is worth writing when none of them matches where your state already lives.

  • Your infrastructure standardises on a database that is neither Redis nor RocksDB.
  • You need job state in the same transaction as your application data.
  • You are testing a failure mode and want a store that can be told to misbehave.
i

Check the built-ins firstInMemoryStore covers tests and short-lived work, and RedisStore covers durable and distributed. See backends before writing anything.

The trait

The Store trait

A store is the single place job state lives, so Store<D, R, P> is broad: it covers job storage, state transitions, counters, locks, events and metrics. The groups are roughly:

GroupMethods
Jobs add_item, add_bulk, add_bulk_only, get_job, fetch_jobs, job_exists, remove, remove_item
State get_state, get_job_ids_in_state, set_fields, exists_in, pop_set, pop_back_push_front, get_delayed_at
Locks & tokens set_lock, get_token, expire, purge_expired
Counters incr, get_counter, get_metrics
Events publish_event, listen_to_events, create_stream_listener, set_event_mode
Progress update_job_progress, update_job_progress_sync
Metrics store_process_metrics, fetch_process_metrics, store_worker_metrics, fetch_worker_metrics
Lifecycle pause, clear_jobs, clear_collections, queue_name, queue_prefix, metadata_field_exists

The generated API reference carries the exact signatures. The existing implementations in src/stores/ are the best worked examples, with InMemoryStore the shortest.

A store must be Clone + Send + 'static, because the queue, every worker and the timer subsystem all hold handles to it.

Conformance

Conformance suites

The kiomq::macros module re-exports the two test suites KioMQ runs against its own stores. Point them at your constructor and you inherit the whole battery.

Both are written for D = R = P = i32. Each takes a unique module name, to keep test names from colliding, and an async expression returning KioResult<S> where S: Store<i32, i32, i32> + Clone + Send + 'static.

Queue behaviour

use kiomq::macros::queue_store_suite;

queue_store_suite!(my_store_queue, async {
    use uuid::Uuid;
    let name = Uuid::new_v4().to_string();
    MyStore::<i32, i32, i32>::new(None, &name).await
});

Worker behaviour

use kiomq::macros::worker_store_suite;

worker_store_suite!(my_store_worker, async {
    use uuid::Uuid;
    let name = Uuid::new_v4().to_string();
    MyStore::<i32, i32, i32>::new(None, &name).await
});

Give each invocation a fresh, uniquely named store. The suites obliterate the queue as they go, so sharing one namespace between them makes the results meaningless.

!

Run them with nextestThe suites share process-global state through the metrics collector, so they need a process each. Use cargo nextest run, not cargo test.

KioMQ's own tests/queue.rs and tests/worker.rs are these macros applied to the in-memory and Redis stores, and are worth copying as a starting point.

Wiring

Wiring it up

Nothing else changes. A queue takes any Store, and processors never see the store type directly:

let store = MyStore::<u64, u64, ()>::new(None, "my-queue").await?;
let queue = Queue::new(store, None).await?;

let worker = Worker::new_async(&queue, processor, Some(WorkerOpts::default()))?;
worker.run()?;

If the store turns out to be generally useful, it is worth a pull request.
